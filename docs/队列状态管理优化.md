# 队列状态管理优化

## 问题描述

原系统在处理 `figma_render_queues` 时存在以下问题：

1. **缺少状态检查**：处理队列时没有检查队列当前状态，可能重复处理已经在处理中的队列
2. **并发安全问题**：多个调度器实例可能同时处理同一个队列
3. **错误处理不完善**：Figma API 返回失败时，错误信息没有保存到 `error_message` 字段
4. **429 错误处理**：429 错误会将状态改回 `waiting`，但没有记录错误信息

## 解决方案

### 1. 添加状态前置检查

**文件**: `internal/services/scheduler.go` - `processQueue()` 方法

在处理队列前，首先检查队列状态是否为 `waiting`：

```go
// ============ 关键检查：只处理 waiting 状态的队列 ============
if queue.Status != "waiting" {
    log.Printf("⏭️ [队列 #%d] 跳过处理（状态: %s，只处理 waiting 状态）", queue.ID, queue.Status)
    return
}
```

**好处**：
- 避免重复处理已经在 `processing` 状态的队列
- 跳过 `completed`、`failed`、`partial` 等终态的队列
- 日志清晰，便于排查问题

### 2. 使用原子更新防止并发

**文件**: `internal/services/scheduler.go` - `processQueue()` 方法

使用数据库的原子操作（WHERE 条件 + UPDATE）来更新状态：

```go
// ============ 原子更新：从 waiting 更新为 processing ============
result := models.DB.Model(&models.FigmaRenderQueue{}).
    Where("id = ? AND status = ?", queue.ID, "waiting").
    Updates(map[string]interface{}{
        "status":     "processing",
        "started_at": now,
        "updated_at": now,
    })

if result.RowsAffected == 0 {
    log.Printf("⚠️ [队列 #%d] 状态已被其他进程修改，跳过处理", queue.ID)
    return
}
```

**好处**：
- 保证只有一个进程能成功更新状态
- 避免并发导致的重复处理
- 使用 `RowsAffected` 检查是否更新成功

### 3. 完善错误处理

#### 3.1 非 429 错误 - 标记为 failed

```go
// ============ 非 429 错误，标记为 failed ============
log.Printf("❌ [队列 #%d] API 调用失败（非速率限制错误），标记为 failed", queue.ID)

now := uint32(time.Now().Unix())
updateErr := models.DB.Model(&models.FigmaRenderQueue{}).
    Where("id = ?", queue.ID).
    Updates(map[string]interface{}{
        "status":        "failed",
        "error_message": fmt.Sprintf("Figma API 错误: %v", err),
        "completed_at":  now,
        "updated_at":    now,
    }).Error
```

**关键点**：
- 设置 `status = 'failed'`，不再重试
- 保存详细的错误信息到 `error_message` 字段
- 设置 `completed_at` 时间戳

#### 3.2 429 错误 - 重新排队

```go
// 429 错误，重新排队等待（Token 冷却由 figma_token_cooldowns 表管理）
log.Printf("⏳ [队列 #%d] 遇到 429 速率限制，重新排队等待", queue.ID)

now := uint32(time.Now().Unix())
updateErr := models.DB.Model(&models.FigmaRenderQueue{}).
    Where("id = ?", queue.ID).
    Updates(map[string]interface{}{
        "status":        "waiting",
        "error_message": fmt.Sprintf("429 速率限制: %v", err),
        "updated_at":    now,
    }).Error
```

**关键点**：
- 状态改回 `waiting`，等待重试
- 保存 429 错误信息，便于追踪
- Token 冷却时间由 `figma_token_cooldowns` 表管理

### 4. 新增辅助函数

**文件**: `internal/services/queue.go`

添加 `UpdateQueueStatusWithError` 函数，用于同时更新状态和错误消息：

```go
// UpdateQueueStatusWithError 更新队列状态并设置错误消息
func (qs *QueueService) UpdateQueueStatusWithError(queueID uint, status string, errorMessage string) error {
    now := uint32(time.Now().Unix())
    
    updates := map[string]interface{}{
        "status":        status,
        "error_message": errorMessage,
        "updated_at":    now,
    }
    
    // 如果是失败或完成状态，设置完成时间
    if status == "failed" || status == "completed" || status == "partial" {
        updates["completed_at"] = now
    }
    
    err := models.DB.Model(&models.FigmaRenderQueue{}).
        Where("id = ?", queueID).
        Updates(updates).Error
        
    if err != nil {
        log.Printf("❌ [Queue] 更新队列状态失败 id=%d: %v", queueID, err)
        return err
    }

    log.Printf("📝 [Queue] 状态更新 id=%d, status=%s, error=%s",
        queueID, status, errorMessage)

    return nil
}
```

## 关键改进点

### ✅ 1. 状态检查

- **问题**：可能重复处理同一队列
- **解决**：处理前检查 `status == 'waiting'`
- **效果**：只处理等待中的队列

### ✅ 2. 原子更新

- **问题**：并发安全问题
- **解决**：使用 `WHERE id = ? AND status = 'waiting'` 原子更新
- **效果**：保证只有一个进程能处理

### ✅ 3. 错误记录

- **问题**：错误信息丢失
- **解决**：所有错误都保存到 `error_message` 字段
- **效果**：便于排查问题

### ✅ 4. 状态明确

- **问题**：失败的队列可能被重复处理
- **解决**：非 429 错误标记为 `failed`，不再重试
- **效果**：避免无意义的重试

## 数据库查询示例

### 查看失败的队列

```sql
SELECT id, file_key, status, error_message, created_at, updated_at
FROM figma_render_queues
WHERE status = 'failed'
ORDER BY updated_at DESC
LIMIT 10;
```

### 查看等待中的队列

```sql
SELECT id, file_key, status, total_nodes, created_at, updated_at
FROM figma_render_queues
WHERE status = 'waiting'
ORDER BY created_at ASC;
```

### 查看处理中的队列（检测卡住的任务）

```sql
SELECT id, file_key, status, started_at, updated_at, 
       (UNIX_TIMESTAMP() - started_at) as processing_seconds
FROM figma_render_queues
WHERE status = 'processing'
  AND started_at > 0
  AND (UNIX_TIMESTAMP() - started_at) > 300  -- 超过5分钟
ORDER BY started_at ASC;
```

## 总结

这次优化确保了：

1. ✅ **只处理 waiting 状态的队列**：避免重复处理
2. ✅ **原子更新防止并发**：保证数据一致性
3. ✅ **完善的错误记录**：所有错误都保存到数据库
4. ✅ **明确的状态流转**：失败不再重试，429 错误重新排队
5. ✅ **详细的日志输出**：便于监控和排查问题

系统现在能够正确处理各种异常情况，避免了无效重试和资源浪费。
